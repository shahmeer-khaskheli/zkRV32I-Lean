# End-to-end verification audit

## Verified chain

The repository has a verified Lean chain for a bounded transcript:

```text
ELF bytes
  -> bounded ELF parse/load
  -> initial MachineState
  -> each checked PC/word/decode/Machine.step pair
  -> output snapshot
  -> BinaryTrace or verified stop prefix
```

The transcript path also creates a finite Rust-memory view for each state and
uses `master_end_to_end_refinement` for step correspondence.

## Accepted stop reasons

| Stop | Lean result |
|---|---|
| Halt | Final state must be `.halted` |
| Fuel limit | Final state must be running; steps and limit must match and be at most 256 |
| Fault | Stop fields must match the modeled fetch, decode, or step fault |

Fault and fuel-limit evidence remain evidence for a verified prefix or stop.
They do not prove termination or total correctness of the binary.

## Trust and attestation

`fuel_limit` is generated by the Rust runner, then independently checked only
for internal consistency with the transcript. It is not attested by hardware,
a separate executor, or a cryptographic proof.

Likewise, a Rust host transcript is a text input to Lean. The implementation
does not prove that a Rust binary process followed the emitted record. The
finite refinement proves correspondence for the modeled finite state and
instruction, not executable Rust source or compiled machine code.

## Remaining work

- General ELF program-header layouts beyond the bounded profile;
- proof of arbitrary-length segment loading order;
- compiler/linker and ELF generation correspondence;
- Rust source extraction or compiled-code equivalence;
- full RV32I and architectural conformance;
- production constraint systems and cryptographic verification.
